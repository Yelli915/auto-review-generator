====================================================================
Ver 3.0 구현 예정: Hugging Face 비전/텍스트 모델 분리 연동 가이드
====================================================================

이 문서는 README.md에서 분리된 별도 구현 계획서입니다.
현재(Ver 2.x)는 Gemini 2.5 Flash 단일 모델이 다음 두 역할을 모두 처리합니다.

  1. 이미지 기반 키워드 추출 (비전 + 구조화 JSON 출력)
  2. 키워드 기반 리뷰 문장 생성 (스트리밍 텍스트)

Ver 3.0에서는 이 두 역할을 Hugging Face의 서로 다른 모델로 분리해서 호출합니다.
아래 순서대로 진행하면 기존 Gemini 흐름을 건드리지 않고 나란히(병행) 추가할 수 있습니다.

※ 이 문서는 api/gemini/ 디렉터리가 api/review/ + api/review/providers/gemini/ 로
  재편된 이후 기준으로 작성되었습니다 (provider 전용 코드와 공용 인프라 분리, 2026-08 작업).


--------------------------------------------------------------------
0. 사전 지식: 지금 코드가 어떻게 연결되어 있는지
--------------------------------------------------------------------

요청 흐름:

  프론트엔드
    -> POST /api/gemini  (api/gemini.js -> api/review/handler.js)
         action: "ping" | "analyze-product" | "keywords" | "review"

  handler.js 안에서:
    - action "keywords" -> generateKeywordResult() (api/review/keywordGeneration.js)
        -> requestGemini() (api/review/providers/gemini/client.js) 로 Gemini 비전 API 호출
    - action "review"   -> streamGeminiReview() (api/review/reviewStreaming.js)
        -> makeStreamUrl() (api/review/providers/gemini/client.js) 로 Gemini 스트리밍 API 호출

설정 상수는 두 곳으로 분리되어 있습니다.
  - api/review/config.js            : provider와 무관한 도메인 규칙
                                       (KEYWORDS_MIN/MAX_COUNT, COSMETIC_CONTEXT_RE,
                                        CONTAINER_*_RE, DEBUG_LOGS, 이미지/요청 크기 제한 등)
  - api/review/providers/gemini/config.js : Gemini 전용 값 (MODEL, 재시도 정책, 토큰 한도)

프롬프트 생성은 api/prompts.js 의 buildKeywordPrompt() / buildReviewPrompt() 가 담당합니다.
이 두 함수는 모델에 종속되지 않는 순수 문자열 생성 함수이므로 Ver 3.0에서도 그대로 재사용합니다.

Ver 3.0에서 새로 만드는 것은 "Gemini API를 호출하는 부분"에 대응하는
"Hugging Face API를 호출하는 부분"입니다. 즉 api/review/providers/gemini/client.js 의
대응품을 api/review/providers/huggingface/ 아래 만드는 작업입니다.
(api/review/, api/review/providers/gemini/ 와 이름 체계를 맞춰 provider 폴더를
 "api/huggingface/"가 아니라 "api/review/providers/huggingface/"에 둡니다.)


--------------------------------------------------------------------
1단계: Hugging Face 계정 및 API 토큰 준비
--------------------------------------------------------------------

1-1. https://huggingface.co 에서 계정 생성 (이미 있으면 생략)

1-2. https://huggingface.co/settings/tokens 에서 Access Token 발급
     - 권한(Role)은 "Read"면 충분합니다 (Inference Providers 호출용).

1-3. https://huggingface.co/settings/inference-providers 에서
     사용할 provider(예: Novita, Together, Hyperbolic 등)가 활성화되어 있는지 확인합니다.
     - 모델마다 서빙하는 provider가 다르고 시간이 지나면 바뀔 수 있으므로,
       실제 구현 시점에 아래 모델 ID들이 여전히 서빙 중인지 반드시 재확인하세요.
     - 확인 방법: 해당 모델의 Hugging Face 모델 페이지 우측 "Inference Providers" 위젯에서
       "Deploy" 대신 바로 호출 가능한 provider가 뜨는지 확인.

1-4. 후보 모델 (실제 사용 전 위 방법으로 서빙 여부 재확인 필수)

     비전 (이미지 -> 키워드):
       - Qwen/Qwen2.5-VL-32B-Instruct   (권장, 다국어/한국어 안정적)
       - Qwen/Qwen2.5-VL-7B-Instruct    (비용/속도 우선 시 대안)
       - OpenGVLab/InternVL3-38B        (대안)

     텍스트 (키워드 -> 리뷰):
       - LGAI-EXAONE/EXAONE-3.5-7.8B-Instruct  (한국어 특화, 권장)
       - upstage/solar-pro-preview-instruct     (대안)
       - Qwen/Qwen2.5-32B-Instruct               (범용 다국어 대안)

--------------------------------------------------------------------
4단계: 비전 클라이언트 작성 (이미지 -> 키워드용)
--------------------------------------------------------------------

Hugging Face Inference Providers는 OpenAI 호환 Chat Completions 스펙을 사용합니다.
이미지는 messages 안에 image_url(base64 data URL) 형태로 넣습니다.

api/review/imageInput.js 의 buildImageParts() 는 Gemini 전용 포맷
({ inline_data: { mime_type, data } })이므로 그대로 쓸 수 없고,
OpenAI 호환 포맷으로 변환하는 함수를 새로 만들어야 합니다.
(참고: buildImageParts()는 현재 api/review/imageInput.js에 있지만 Gemini 전용
 wire format이므로, 이번 작업에서 api/review/providers/gemini/client.js 쪽으로
 옮기는 것도 함께 고려하세요. 검증 로직(validateImageInput 등)은 계속 imageInput.js에 둡니다.)

  파일: api/review/providers/huggingface/visionClient.js
  --------------------------------
  import { createJsonHeaders, readJsonSafely } from '../../../../shared/httpJson.js'
  import { HF_ROUTER_URL, HF_VISION_MODEL, HF_KEYWORDS_MAX_OUTPUT_TOKENS } from './config.js'

  // api/review/imageInput.js 의 validateImagesInput() 결과를 그대로 받는다고 가정
  // (images: [{ imageBase64, mimeType }])
  export function buildVisionMessageContent(images, promptText) {
    const imageContents = images.map((image) => ({
      type: 'image_url',
      image_url: {
        url: `data:${image.mimeType};base64,${image.imageBase64}`,
      },
    }))
    return [...imageContents, { type: 'text', text: promptText }]
  }

  export async function requestHfVisionKeywords({ key, images, promptText }) {
    const response = await fetch(HF_ROUTER_URL, {
      method: 'POST',
      headers: createJsonHeaders({ Authorization: `Bearer ${key}` }),
      body: JSON.stringify({
        model: HF_VISION_MODEL,
        messages: [
          {
            role: 'user',
            content: buildVisionMessageContent(images, promptText),
          },
        ],
        max_tokens: HF_KEYWORDS_MAX_OUTPUT_TOKENS,
        temperature: 0.1,
      }),
    })

    const data = await readJsonSafely(response)
    if (!response.ok) {
      const message = data?.error?.message || `요청 실패 (HTTP ${response.status})`
      return { ok: false, error: message, status: response.status }
    }

    const text = data?.choices?.[0]?.message?.content ?? ''
    return { ok: true, text, model: HF_VISION_MODEL }
  }

주의: Gemini의 responseSchema 같은 강제 JSON 스키마 기능이 없는 provider가 많습니다.
따라서 프롬프트(buildKeywordPrompt) 마지막의
'- JSON만 출력합니다.' 지시에 의존해서 텍스트로 받은 뒤,
기존 api/review/keywordGeneration.js 의 parseKeywordsFromText() 파서를
그대로 재사용해 파싱합니다 (5단계 참고). 이 파서는 이미 코드펜스 제거,
느슨한 JSON 복구, 줄 단위 폴백까지 처리하므로 새로 만들 필요가 없습니다.


--------------------------------------------------------------------
5단계: keywordGeneration.js 에 provider 분기 추가
--------------------------------------------------------------------

api/review/keywordGeneration.js 의 generateKeywordResult() 안에서
Gemini 호출 부분만 provider에 따라 분기합니다. 파싱/필터링 로직(parseKeywordsFromAny,
filterCosmeticContainerKeywords, 중복 방지 재시도 루프)은 모델과 무관하므로 그대로 둡니다.

변경 지점 (api/review/keywordGeneration.js, requestGemini 호출부):

  result = await requestGemini({
    key,
    payload: buildKeywordPayload(promptForAttempt),
  })

이 부분을 provider 인자를 받는 형태로 바꿉니다.

  파일: api/review/keywordGeneration.js 수정 예시
  --------------------------------
  import { requestGemini } from './providers/gemini/client.js'
  import { requestHfVisionKeywords } from './providers/huggingface/visionClient.js'

  async function requestKeywordCompletion({ provider, key, promptForAttempt, imageInput, buildKeywordPayload }) {
    if (provider === 'huggingface') {
      return requestHfVisionKeywords({
        key,
        images: imageInput?.images ?? [],
        promptText: promptForAttempt,
      })
    }
    return requestGemini({ key, payload: buildKeywordPayload(promptForAttempt) })
  }

  // 루프 안에서:
  result = await requestKeywordCompletion({
    provider: body.provider ?? process.env.AI_PROVIDER ?? 'gemini',
    key,
    promptForAttempt,
    imageInput,
    buildKeywordPayload,
  })

  // 결과 텍스트 추출부도 provider별로 분기
  const text = provider === 'huggingface'
    ? result.text
    : gatherKeywordResponseText(result.data)
  parsed = { ...parseKeywordsFromText(text) && { keywords: parseKeywordsFromText(text) }, rawText: text }

실제로는 gatherKeywordResponseText()/parseKeywordsFromAny() 내부에서
Gemini 응답 구조(data.candidates[...])를 직접 참조하므로,
provider별로 "원문 텍스트를 뽑아내는 함수"만 분리하고
그 이후 파싱(parseKeywordsFromText)은 공통으로 쓰는 방식을 권장합니다.


--------------------------------------------------------------------
6단계: 텍스트(리뷰) 스트리밍 클라이언트 작성
--------------------------------------------------------------------

Hugging Face Inference Providers는 stream: true 옵션으로
OpenAI 호환 SSE 스트리밍을 지원하는 provider가 있습니다 (모델/provider별로 확인 필요).
청크 형식은 Gemini와 다르므로 (Gemini: candidates[0].content.parts[0].text,
HF/OpenAI 호환: choices[0].delta.content) 파싱 부분만 새로 작성합니다.

  파일: api/review/providers/huggingface/textClient.js
  --------------------------------
  import { createJsonHeaders, readJsonSafely } from '../../../../shared/httpJson.js'
  import { HF_ROUTER_URL, HF_TEXT_MODEL, HF_REVIEW_MAX_OUTPUT_TOKENS } from './config.js'

  export async function streamHfReview({ key, prompt, length, res, setCommonSecurityHeaders }) {
    const response = await fetch(HF_ROUTER_URL, {
      method: 'POST',
      headers: createJsonHeaders({ Authorization: `Bearer ${key}` }),
      body: JSON.stringify({
        model: HF_TEXT_MODEL,
        messages: [{ role: 'user', content: prompt }],
        max_tokens: HF_REVIEW_MAX_OUTPUT_TOKENS[length] ?? HF_REVIEW_MAX_OUTPUT_TOKENS.medium,
        temperature: 0.6,
        stream: true,
      }),
    })

    if (!response.ok) {
      const data = await readJsonSafely(response)
      throw new Error(data?.error?.message || '리뷰 생성 실패')
    }
    if (!response.body) throw new Error('스트리밍 응답 본문이 없습니다.')

    res.statusCode = 200
    setCommonSecurityHeaders(res)
    res.setHeader('Content-Type', 'application/x-ndjson; charset=utf-8')
    res.setHeader('Cache-Control', 'no-cache, no-transform')
    res.setHeader('X-Accel-Buffering', 'no')

    const reader = response.body.getReader()
    const decoder = new TextDecoder()
    let buffer = ''
    let fullText = ''

    const writeJsonLine = (payload) => res.write(`${JSON.stringify(payload)}\n`)

    const handleSsePayload = (payload) => {
      if (!payload || payload === '[DONE]') return
      try {
        const json = JSON.parse(payload)
        const delta = json?.choices?.[0]?.delta?.content
        if (delta) {
          fullText += delta
          writeJsonLine({ text: delta })
        }
      } catch {
        // 부분 청크는 무시, 다음 read()에서 이어붙여 처리
      }
    }

    while (true) {
      const { done, value } = await reader.read()
      if (done) break
      buffer += decoder.decode(value, { stream: true })
      const lines = buffer.split('\n')
      buffer = lines.pop() || ''
      for (const line of lines) {
        if (!line.startsWith('data: ')) continue
        handleSsePayload(line.slice(6).trim())
      }
    }

    writeJsonLine({ done: true })
    res.end()
    return fullText
  }

api/review/reviewStreaming.js 의 streamGeminiReview() 와 거의 동일한 뼈대를 유지했습니다.
minReviewChars 검증, normalizeReviewText() 같은 후처리 로직은 원본 파일에서 가져와
동일하게 적용하세요 (모델과 무관한 공통 로직입니다).

7단계: handler.js 에 provider 스위치 연결
--------------------------------------------------------------------

api/review/handler.js 의 handleKeywords()/handleReview() 에서
provider를 결정해 각 함수에 넘깁니다. 이렇게 하면 환경변수(AI_PROVIDER)나
요청 바디의 provider 필드로 Gemini/HF를 전환할 수 있어,
운영 중인 서비스를 끊지 않고 점진적으로 검증할 수 있습니다.

  파일: api/review/handler.js 수정 지점
  --------------------------------
  function resolveProvider(body) {
    const requested = typeof body.provider === 'string' ? body.provider.trim() : ''
    if (requested === 'huggingface' || requested === 'gemini') return requested
    return process.env.AI_PROVIDER === 'huggingface' ? 'huggingface' : 'gemini'
  }

  function getHuggingFaceApiKey() {
    return typeof process.env.HUGGINGFACE_API_KEY === 'string'
      ? process.env.HUGGINGFACE_API_KEY.trim()
      : ''
  }

  // handleKeywords / handleReview 안에서 provider === 'huggingface' 일 때
  // getGeminiApiKey() 대신 getHuggingFaceApiKey() 를 사용하고,
  // generateKeywordResult / streamGeminiReview 대신
  // 5, 6단계에서 만든 함수를 호출하도록 분기합니다.

프론트엔드 변경 없이도 서버 환경변수 AI_PROVIDER 하나로 전체 스위치가 가능하고,
필요하면 요청 바디에 provider 필드를 추가해 A/B 테스트도 가능합니다.
(src/components/ReviewGenerator/api/geminiService.js 는 여전히 /api/gemini 로만
 요청을 보내므로, provider 전환이 서버 쪽에만 있는 한 프론트엔드 수정은 필요 없습니다.)

8단계: 로컬에서 동작 확인
--------------------------------------------------------------------

8-1. .env.local 에 HUGGINGFACE_API_KEY, HF_VISION_MODEL, HF_TEXT_MODEL, AI_PROVIDER=huggingface 설정

8-2. 개발 서버 실행

    vercel env pull .env.local
    npm run dev:vercel

8-3. curl 로 키워드 생성 확인 (이미지 base64는 짧은 테스트 이미지로 대체)

    curl -X POST http://localhost:3000/api/gemini \
      -H "Content-Type: application/json" \
      -H "Authorization: Bearer <google-id-token>" \
      -d '{
        "action": "keywords",
        "provider": "huggingface",
        "rating": 4,
        "category": "product",
        "images": [{ "imageBase64": "<base64>", "mimeType": "image/jpeg" }]
      }'

8-4. curl 로 리뷰 스트리밍 확인

    curl -N -X POST http://localhost:3000/api/gemini \
      -H "Content-Type: application/json" \
      -H "Authorization: Bearer <google-id-token>" \
      -d '{
        "action": "review",
        "provider": "huggingface",
        "rating": 4,
        "category": "product",
        "keywords": ["촉촉함", "향", "발림감"],
        "length": "medium",
        "tone": "neutral"
      }'

8-5. 응답 JSON의 keywords 개수, 리뷰 문장의 자연스러움을 Gemini 결과와 비교합니다.
     JSON 파싱 실패가 잦으면 prompts.js 의 buildKeywordPrompt() 출력 형식 지시문에
     few-shot 예시(정상 출력 1개)를 추가해 모델을 유도하세요.

10단계: 문서 반영

  - provider 가용성이 시간에 따라 바뀌므로 모델 ID를 하드코딩하지 않고 환경변수로 유지 (2단계 참고)
  - 장점: 모델 선택 유연성 확보, 특정 제공사 rate limit/quota 정책에 대한 단일 의존 제거
